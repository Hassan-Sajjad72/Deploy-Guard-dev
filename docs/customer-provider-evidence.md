Customer execution stays unavailable until separately authorized final AWS checks finish. Local SDK mocks, syntax checks and executable integrity hashes do not certify deployment readiness.

The backend validates `DEPLOYGUARD_FINAL_PROVIDER_PROOFS`, an array of `{proof, signature}` envelopes. `HostingProfileRegistryService` defines the exact `deployguard.final-provider-proof/v1` schema and required checks: deploy, retry, rollback, ownership, cleanup, actual AWS runtime and budget. Each check retains the SHA-256 of its real evidence artifact. A proof names one profile, region, AWS account and adapter executable fingerprint. The final approver, approval ID, verified time and expiry are mandatory. Proof expiry is at most 90 days. Unsigned, stale or source-mismatched evidence cannot activate a profile. ECS source integrity is calculated from the complete versioned workflow and its executable contracts, including variables, outputs and protected credential helper; legacy workflow hashes remain independently checked.

The operator must configure a separate `DEPLOYGUARD_FINAL_PROVIDER_APPROVAL_ID` and a private signing key of at least 32 characters in `DEPLOYGUARD_FINAL_PROVIDER_PROOF_SIGNING_KEY`. A signature is HMAC-SHA256 over `planFingerprint(proof)`, the canonical JSON SHA-256 exported by `deployment-plan.ts`. Keep the key outside repositories, HTTP responses and browser configuration. Empty example configuration enables no profiles. Changing executable hashes, proof fingerprint or region requires a fresh plan and approval.

A profile proof does not grant a customer account mutation authority. An authenticated platform operator or super administrator, after recent password verification, imports a separately signed `deployguard.customer-authority-proof/v1` envelope through `POST /api/admin/workspaces/:organizationId/aws-bindings/:bindingId/final-authority-proof` with `proof`, `signature` and a reason. The schema is defined in `customer-authority-proof.ts`. Its binding version, role, account, complete region list and explicit project IDs must match fresh read-verified ownership. It requires real trust, temporary credential, resource ownership, IAM permission, rollback/cleanup and platform-account isolation evidence. The signed final actor ID must match the importing operator; expiry is at most 30 days. The import locks the binding and rechecks active organization, project ownership and operator identity, then retains an audit event. Revocation, re-verification, project archive, evidence expiry or signing-key changes revoke customer mutations. No AWS API is called by evidence import.

Customer GitHub execution assumes the same configured control-plane role trusted by the customer binding, reads a protected Secrets Manager binding record and chains into the approved customer role using its private external ID. Only the protected secret ARN and nonsecret plan/account/workload inputs are dispatched. The workflow checks role, account, binding version, approved project, region and authority expiry before using customer credentials. Resource previews seal the VPC, public subnets and customer Terraform state bucket. Temporary credentials and external IDs are excluded from plans, pipeline inputs, stored runtime manifests and audit metadata.

Current remaining gates include complete workload-specific prices, final real-provider evidence and customer lifecycle approval contracts for rollback/cleanup. Provider profiles with no implemented adapter registration remain unavailable. Importing an evidence document cannot replace missing runtime code or correct an unsafe IAM policy.
