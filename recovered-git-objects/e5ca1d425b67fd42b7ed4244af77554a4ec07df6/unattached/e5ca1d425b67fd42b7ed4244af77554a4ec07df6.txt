# DeployGuard Final Product Simplification and Integration Plan — FINAL

**Status:** Specification frozen and implementation authority  
**Primary goal:** Convert DeployGuard into a simple GitHub-first, one-click deployment product while preserving the technical depth required for the FYP.  
**Execution rule:** Codex completes one integration iteration, updates this file, reports the result, and stops. In the same Codex session, the operator replies only **`Continue`** to start the next incomplete iteration.

---

## 1. Final product decision

DeployGuard will use:

- **GitHub OAuth as the only user sign-in method**
- **DeployGuard GitHub App** for repository authorization
- **GitHub Actions as the only deployment execution engine**
- **AWS OIDC temporary credentials** for GitHub Actions
- **Docker, ECR, Terraform, ECS Fargate and ALB** for deployment
- **PostgreSQL** for product state, operation history and audit evidence

The normal user must not configure:

- AWS access keys or secret keys
- AWS role ARNs
- GitHub PATs or workflow names
- Terraform backend settings
- container ports owned by DeployGuard
- `HOST`, `PORT` or `NODE_ENV`
- Redis, BullMQ or worker processes

The normal user provides only:

- GitHub authorization
- repository
- branch
- optional pasted application `.env` content
- one Deploy click

- Deploying projects
- Live projects
- Failed projects, because they require logs/retry
- Destroyed projects, because they retain history and support Deploy Again

## 6.2 New Deployment

### GitHub App not connected

```text
Connect your repositories

[ Install GitHub App ]
```

After installation, return automatically to `/deploy`.

### GitHub App connected

Show only:

```text
Repository
[ Select repository ]

Branch
[ Select branch ]

Environment file — Optional
[ Paste `.env` content here ]

[ Deploy ]
```

### Environment-variable policy

- Present one multiline paste area, not a key/value row builder.
- Accept ordinary `.env` syntax such as `KEY=value`, blank lines and comments.
- Parse client-side only for immediate syntax feedback; the backend remains authoritative.
- Reject duplicate keys, malformed names and unsupported multiline secret syntax with clear line numbers.
- Never echo stored secret values after save; show only key names and masked status.
- Preserve comments only when safe and useful; do not log secret values.
- Exclude platform-owned keys such as `PORT`, `HOST`, `NODE_ENV`, AWS credentials and GitHub tokens.
- The user may leave the area empty.
- Likely missing application variables create a warning, not an automatic deployment block.
- Editing `.env` after deployment is a modal/action from Project Overview and requires redeploy to take effect.


Example warning:

```text
This repository may require DATABASE_URL.
You can continue without it, but the application may fail.

[ Deploy Anyway ]
```

### Structural blockers

Deployment must stop before workflow dispatch and AWS mutation when:

- repository is empty
- repository or branch cannot be accessed
- language/framework is unsupported
- dependency manifest is missing
- application root is unsafe or ambiguous
- no usable build/start strategy exists
- workflow cannot be created or verified

Show one simple inline message. Do not redirect to separate Detection or Pre-flight pages.

## 7. Destroy workflow

```mermaid
flowchart TD
    A["Live application<br/>100%"] --> B["Click Destroy"]
    B --> C["Confirmation popup"]
    C --> D{"Confirm destroy?"}

    D -- "No" --> A
    D -- "Yes" --> E["Destroy running banner/popup"]

    E --> F["Dispatch GitHub Actions destroy"]
    F --> G["Terraform destroy"]
    G --> H["Remove ECS, ALB, ECR and managed resources"]
    H --> I["Reconcile S3 state and operation history"]

    I -- "Failure" --> J["Destroy failed banner<br/>View logs / Retry"]
    I -- "Success" --> K["Banner changes to Destroy completed"]
    K --> L["User clicks Close"]
    L --> M["Project returns to Ready to Deploy"]
    M --> N["Deploy Again"]
```

### Required behavior

During destroy:

- show a persistent running popup/banner
- disable Deploy, Redeploy and duplicate Destroy
- provide a View Progress action
- preserve the live URL until destruction is confirmed complete, or clearly mark it as being removed

After successful destroy:

- change the running popup into a **Destroy completed** state
- show a clear **Close** button
- close only when the user clicks Close
- remove the live URL
- remove the 100% Live state
- keep repository analysis and configuration
- return the page to **Ready to Deploy**
- show **Deploy Again**
- preserve all deployment and destroy history
- make the main Overview body show only **Deploy Again**
- hide Monitoring and active Infrastructure navigation
- keep historical Pipeline attempts available through Pipeline & Recovery
- do not show live application logs after destroy; only retained historical pipeline evidence may be viewed

Do not fake backward progress from 100% through the deployment phases.

## 9. Stack detection maturity contract

Stack detection remains automatic and mostly invisible to the normal user, but it must produce a trustworthy deployment contract before any workflow dispatch or AWS mutation.

### Required detection outputs

For every analyzed repository and selected branch, persist:

- repository commit SHA used for analysis
- detected application roots
- primary application root selected for deployment
- language and runtime
- framework
- package manager and lockfile
- install command
- build command
- production start command
- application port
- health-check path
- output/artifact directory where applicable
- static, server-rendered, API, worker or mixed workload classification
- Dockerfile strategy: repository-provided, generated template or unsupported
- required and optional application environment-variable names
- persistent-storage requirement when evidence exists
- confidence level and evidence for each important inference
- structural blockers, warnings and unresolved ambiguity

### Maturity rules

- Detection must be based on repository evidence, not filename guesses alone.
- Selected branch and exact commit must be part of the detection cache key.
- A stale detection result must never be reused after the commit changes.
- Monorepositories must be scanned for multiple candidate application roots.
- The detector must rank candidates and explain why one was selected.
- Ambiguous candidates must block automatic deployment unless a safe deterministic choice exists.
- Existing user Dockerfiles may be used only after safety and deployability validation.
- Generated Dockerfiles must use centralized templates with pinned versions.
- `PORT`, `HOST`, `NODE_ENV`, AWS credentials and GitHub tokens must not be treated as user-owned required environment variables.
- Likely missing application environment variables may produce warnings without blocking Deploy.
- Missing build/start evidence, inaccessible roots and structurally unsupported repositories must block before GitHub Actions dispatch.
- Detection failures must return one concise user-facing blocker plus expandable technical evidence.
- Detection must be idempotent and reproducible for the same repository, branch and commit.
- Manual overrides must be limited, explicit, validated and auditable; they must not silently replace detector evidence.

### Supported maturity targets

At minimum, test representative fixtures for:

- Node.js with npm, yarn and pnpm
- Express or similar Node API
- React/Vite static frontend
- Next.js server-rendered application
- Python with `requirements.txt`
- Python with `pyproject.toml`
- Django
- FastAPI
- repository-provided Dockerfile
- monorepository with frontend and backend applications
- nested application root
- empty repository
- unsupported repository
- ambiguous multiple application roots
- missing production start command
- environment-variable references without provided values

### User experience

The normal New Deployment page must remain simple:

```text
Repository
Branch
Optional environment variables
Deploy
```

Detection runs silently after repository and branch selection. Only these outcomes are shown:

- ready to deploy
- non-blocking warning
- one actionable structural blocker

Full evidence is available only through Developer details or authorized diagnostics.


## 10. Legacy retirement rules

The GitHub Actions path is authoritative.

Remove or disconnect all production dependencies on:

- legacy release lanes
- Redis/BullMQ deployment queues
- deployment outbox drain
- infrastructure-plan workers
- infrastructure-apply workers
- release workers
- worker capability registration
- deployment leases and worker fencing
- legacy progress denominators
- old mutation routes
- old normal-v1 scripts
- old frontend controls

Deletion must be dependency-aware:

1. Replace every active reader/projector/route with the GitHub Actions operation model.
2. Verify builds and live routes.
3. Remove unreachable providers, scripts and source.
4. Preserve only historical database evidence required for audit/history.
5. Prove no normal product path can invoke the retired system.

## 11. Expert implementation guardrails

These requirements strengthen the existing product plan without adding pages or expanding the normal user journey.

### 11.1 One authoritative project-state projection

The backend must expose one canonical current-state projection used by:

- Projects
- Project Overview
- Pipeline & Recovery
- Infrastructure & FinOps
- Monitoring
- Admin project visibility

No frontend page may independently infer the current project state from unrelated records.

Canonical states:

```text
READY
DEPLOYING
FAILED
LIVE
DESTROYING
DESTROYED
```

The projection must include:

- current state and reason
- active operation ID and type
- latest completed operation
- repository, branch and commit
- active deployment URL when valid
- whether active infrastructure exists
- current application-health status
- current monitoring availability
- last reconciliation time
- evidence source and freshness

A historical failure must never override a newer successful, destroying or destroyed state.

### 11.2 Deployment success versus application health

A successful GitHub Actions workflow is necessary but is not enough to mark the project **LIVE**.

The project becomes LIVE only after:

```text
GitHub Actions completed successfully
→ Terraform apply completed
→ ECS service became stable
→ ALB target became healthy
→ configured application health endpoint responded successfully
```

If infrastructure was created but the application is unhealthy:

- do not label the project LIVE
- preserve the infrastructure evidence
- show a truthful failed or degraded result
- route the user to Pipeline & Recovery
- provide Retry only when the operation is eligible

### 11.3 Historical evidence after destroy

After successful destroy, retain:

- deploy, retry, redeploy and destroy attempts
- sanitized pipeline logs
- audit events
- last deployed repository, branch and commit
- historical infrastructure summary
- previous cost estimate
- destroy-verification evidence

Historical information must be labelled as **Historical**, **Last deployment** or **Last known infrastructure**. It must never be displayed as active cloud infrastructure, current monitoring or a live application.

### 11.4 Truthful unavailable and stale states

Never replace missing evidence with zero values, mock values or visually convincing placeholders.

Use explicit states such as:

```text
Cost estimate unavailable
Metrics integration unavailable
Waiting for first Prometheus scrape
Monitoring data is stale
No active infrastructure
Health verification pending
```

Every external-data surface must show its source, last-updated time, freshness or stale state, and the unavailable reason when known.

### 11.5 Read-focused Admin boundary

The minimum Admin panel remains read-focused.

Admin may:

- view platform health
- view users and roles
- assign supported roles
- disable or re-enable product access
- inspect all projects and operations
- inspect audit logs

Admin must not:

- impersonate users
- reveal OAuth tokens or application secrets
- directly deploy, redeploy or destroy another user's project
- bypass project ownership for mutation
- silently alter application environment values

Any future privileged mutation requires a separate authorization design and explicit audit requirements.

### 11.6 Truthful visual progress

Visual polish must communicate real state, not simulated completion.

- Progress advances only from authoritative backend or external evidence.
- Waiting animations may indicate activity but must not increase progress.
- A workflow waiting on GitHub or AWS may remain on the same phase.
- Success animation appears only after application-health verification.
- Failure treatment must preserve the failed phase and evidence.
- Reduced-motion preferences must be respected.

### 11.7 Idempotent mutations and ownership

Deploy, Retry, Redeploy and Destroy must be idempotent and mutually controlled.

For every stateful mutation:

```text
Validate exact scope and evidence
→ acquire ownership/lock
→ create or reuse one operation
→ execute once
→ verify external and internal state
→ persist truthful evidence
→ release ownership and stop
```

Required protections:

- repeated clicks reuse or reject against the active operation
- one project cannot run conflicting deploy and destroy operations
- retries inspect remote and database state before dispatching again
- backend restart does not create a duplicate operation
- GitHub Actions dispatch uses a stable correlation/idempotency key
- every operation has an owner, type, status and audit trail



## Specification freeze and deviation control

This document is now frozen for implementation.

Codex must not:

- add new normal-user pages
- restore email/password authentication
- request AWS credentials, GitHub PATs or Terraform settings from users
- replace the pasted `.env` flow with key/value rows
- merge Pipeline, Infrastructure and Monitoring concerns
- expose Detection, Pre-flight, Environment, Cost or FinOps as separate sidebar pages
- mark a project LIVE before application health is verified
- simulate progress, monitoring, cost or infrastructure evidence
- re-enable retired Redis/BullMQ/custom-worker execution
- change the approved light visual direction without a reproduced accessibility or implementation defect

A deviation is allowed only when Codex proves one of the following:

1. the requirement is technically contradictory with the existing verified architecture;
2. implementing it would create a security, credential-exposure or data-loss risk;
3. an unavoidable external platform limitation blocks the exact behavior.

Any allowed deviation must be recorded in the Progress Ledger with:

- exact evidence
- affected requirement
- smallest safe alternative
- tests proving the alternative

# 15. Final information-architecture decisions

1. **Landing:** only the product promise, Deploy and role-gated Admin.
2. **Projects:** keep all projects with a real deployment attempt, including Failed and Destroyed; exclude abandoned drafts.
3. **Overview:** one generic, state-based page. Do not keep duplicate Overview and Deployments destinations.
4. **Pipeline:** owns CI/CD phases, attempts, logs, failure evidence, AI troubleshooting and retry.
5. **Detection/Pre-flight:** automatic and hidden; evidence appears only in Developer details.
6. **Environment:** no sidebar page. Use one pasted `.env` area during setup and an Edit `.env` modal later.
7. **Infrastructure:** keep the page; it owns resource inventory, FinOps and Terraform ZIP export.
8. **Monitoring:** Prometheus/Grafana plus ECS/ALB health; visible only while deployed.
9. **Admin:** top-right role-gated action; minimal Overview, Users/Roles, Projects/Operations and existing Audit Log.
10. **Destroyed state:** completion banner waits for Close, Overview shows Deploy Again, Monitoring disappears, and historical pipeline attempts remain available.
11. **State authority:** every page consumes one backend current-state projection.
12. **Live status:** requires successful workflow, stable ECS service, healthy ALB target and successful endpoint verification.
13. **Historical evidence:** retained after destroy and labelled as historical, never active.
14. **Unavailable data:** represented explicitly and never replaced by fake zero values.
15. **Admin boundary:** read-focused with roles/access management, no impersonation or cross-owner cloud mutation.
16. **Progress:** driven by real evidence, not timers.
17. **Mutations:** Deploy, Retry, Redeploy and Destroy are idempotent and mutually controlled.
