Executive product charter — the target product (read this section before R0)
Product: DeployGuard, an AWS-first intelligent client-delivery and operations control plane for small/mid-sized AWS consultancies, DevOps service providers and software agencies operating multiple client applications. Secondary later audience: internal platform engineering teams. Not a generic cheap PaaS, an unrestricted AWS chatbot, an AWS replacement, or an AWS DevOps Agent clone. Commercial differentiation is a product hypothesis until validated with paying customers.
Buyer job: take an authorized client repository and business constraints; discover requirements; design compatible AWS choices; compare full costs/risks; approve and provision infrastructure; build/release/verify/roll back; observe and explain incidents; recommend measured optimizations; execute only approved, bounded remediation; and deliver a complete client-owned operational handoff. North-star workflow: client engagement → application analysis → constraints/architecture choices → verified plan + cost/security review → approved infrastructure and deployment → monitored operations + safe optimization → evidence-backed handoff.
Confirmed working direction: AWS only for initial release; owner's existing AWS account for controlled prototype/testing only (does not authorize spend or deployment); existing modular NestJS monolith / React frontend / GitHub Actions / pinned Railpack / Terraform / ECS Fargate remain foundation. No microservice migration, no speculative cloud spending, no automated destructive actions, no undocumented cross-tenant resource sharing. Build a professional engineering product, but prioritize one validated buyer workflow over copying every incumbent feature.
Agency capabilities: separate customer/client workspaces, engagements, environment/resource ownership, secure role boundaries, per-client cost attribution, change history, reusable company standards, approvals, operational evidence, and exportable client handoff. Commercial SaaS management: customer organization administration and a separate, hardened DeployGuard operator/super-admin plane for user and organization lifecycle, subscription/entitlements, payment and invoice state, abuse/suspension actions, platform health and support; design is mandatory, implementation gated by agreed commercial policy. Future bring-your-own AWS account (BYOC) is a design requirement but not assumed approved for production; separate per-client AWS accounts are preferred for strong isolation once certified. Never represent simple app-level RBAC in one AWS account as equivalent to isolated tenant infrastructure.
User requests and constraints: free-text intent can initiate analysis and preview, never direct arbitrary shell, AWS API or Terraform mutation. “Cheapest” means lowest comparable total estimated cost satisfying explicit availability, security, performance, region, data and operational constraints; unknown pricing/usage invalidates a cheapest claim. Application-specific CPU/memory and scaling must be evidence- or telemetry-driven, not hardcoded blanket thresholds. Diagnosis must distinguish observed facts from hypotheses; remediation requires reviewed runbook, authorization, spend cap, rollback/verification and audit. Preserve visibility into AWS architecture and resources.
Status terms: EXISTING_SOURCE_REVIEWED, LOCAL_TESTED, AWS_VERIFIED, PLANNED, EXPERIMENTAL, BLOCKED. Existing GitHub code is not presumed fully tested or production-ready. The implementation status of every capability must be determined from the current repository and real evidence, not from this document.
Measurable commercial target to validate: a DevOps service team can deploy and hand over a representative client application with fewer manual operations and less incident/ownership ambiguity than its current workflow. Track time-to-verified-handoff, % successful reproducible deployments, rollback safety, incorrect recommendations, total AWS cost estimate error, engineer review time, incident diagnosis evidence quality, and whether teams commit to a paid pilot. No guaranteed savings or market superiority without controlled comparisons.

Product contract: what a successful DeployGuard experience looks like
A user connects GitHub, selects a repository/branch and environment, and receives a source-SHA-pinned analysis preview. DeployGuard discovers deployable applications, explains build/ENV/external-dependency requirements, presents only eligible hosting profiles with assumptions and estimates, and asks for the minimum missing inputs. After explicit selection/confirmation it builds once per immutable plan, deploys via the chosen adapter, verifies the public result, and shows status from authoritative evidence. It can redeploy, roll back to a recorded immutable release and destroy only resources proven to belong to the project. The same UX and lifecycle concepts must hold for ECS, static hosting and the chosen low-cost provider. Unsupported/ambiguous applications receive a useful diagnosis, not guessed infrastructure.
Required shared interfaces (introduce only when their milestone begins)
    • RepositorySnapshot: repository identifier, user-selected branch, exact 40-char source SHA, checkout ownership, analysis timestamp and safe path boundaries. Every analyzer consumes the same immutable snapshot; never silently re-resolve the moving branch mid-operation.
    • ServiceAnalysis: stable service ID/directory, evidence-backed application kind (static | http_service | worker), language/framework/provider confidence, manifest/lockfile pointers, workspace dependencies, candidate ports and unresolved/conflicting evidence.
