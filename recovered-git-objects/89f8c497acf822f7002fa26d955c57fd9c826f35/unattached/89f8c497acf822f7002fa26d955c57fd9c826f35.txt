# DeployGuard Final Product Simplification and Integration Plan

**Status:** Implementation authority  
**Primary goal:** Convert DeployGuard into a simple GitHub-first, one-click deployment product while preserving the technical depth required for the FYP.  
**Execution rule:** Codex completes one integration iteration, updates this file, reports the result, and stops. In the same Codex session, the operator replies only **`Continue`** to start the next incomplete iteration.

---

## 1. Final product decision

DeployGuard will use:

- **GitHub OAuth as the only user sign-in method**
- **DeployGuard GitHub App** for repository authorization
- **GitHub Actions as the only deployment execution engine**
- **AWS OIDC temporary credentials** for GitHub Actions
- **Docker, ECR, Terraform, ECS Fargate and ALB** for deployment
- **PostgreSQL** for product state, operation history and audit evidence

The normal user must not configure:

- AWS access keys or secret keys
- AWS role ARNs
- GitHub PATs or workflow names
- Terraform backend settings
- container ports owned by DeployGuard
- `HOST`, `PORT` or `NODE_ENV`
- Redis, BullMQ or worker processes

The normal user provides only:

- GitHub authorization
- repository
- branch
- optional application-owned environment variables
- one Deploy click

## 3. Absolute minimum page architecture

Use exactly **seven product routes**.

| # | Page | Route | Purpose |
|---|---|---|---|
| 1 | Home / GitHub Login | `/` | GitHub sign-in, Deploy button, compact project list |
| 2 | New Deployment | `/deploy` | GitHub App connection, repository, branch, optional ENV and Deploy |
| 3 | Project / Deployment | `/projects/:projectId` | Progress, live result, redeploy and destroy |
| 4 | Logs & Recovery | `/projects/:projectId/logs` | Failure evidence, AI troubleshooting, retry and attempt history |
| 5 | Infrastructure | `/projects/:projectId/infrastructure` | AWS, Terraform, ECR, ECS, ALB, state and cost evidence |
| 6 | Monitoring | `/projects/:projectId/monitoring` | Real deployment health, ECS/ALB status and GitHub Actions activity |

### Visual design direction

The simplified workflow must feel modern and memorable, not like a plain administrative dashboard.

#### Brand palette

Use a dark-first DeployGuard theme with reusable design tokens:

| Token | Value | Use |

The main brand treatment may use a restrained gradient:

```text
linear-gradient(135deg, #7C3AED 0%, #A855F7 52%, #22D3EE 100%)
```

Use this gradient only for the main Deploy/Continue button, selected progress treatment and limited hero emphasis. Do not apply it to every card.

#### Required visual elements

- a subtle radial glow or technical grid in major empty backgrounds
- recognizable GitHub, repository, branch, environment, build, cloud and health icons
- a five-phase deployment rail with icons and a clear animated active state
- compact status chips for Ready, Deploying, Live, Failed and Destroying
- attractive project cards showing repository, branch, current state and last update
- soft elevation, 12–16px corner radii and restrained borders
- meaningful hover, pressed, loading and disabled states
- skeleton loading rather than blank screens
- small transitions for page/state changes, normally 150–250ms
- success check animation and a clear failure treatment
- a distinct destructive confirmation modal and destroy-running banner

#### Visual restraint

Do not use:

- large empty white or gray areas
- unrelated colors on every component
- excessive glassmorphism
- constant animations
- gradients behind long body text
- fake charts or decorative infrastructure data
- tiny low-contrast text
- raw technical identifiers as visual labels

#### Accessibility

- meet WCAG AA contrast for normal text and controls
- never communicate state through color alone
- pair status colors with icons and text
- preserve keyboard focus indicators
- respect reduced-motion preferences
- use readable type sizes and touch/click targets

#### Design-system rule

Create shared tokens and reusable components before styling individual pages. No page may introduce private hard-coded colors when an equivalent token exists.


### GitHub App connected

Show only:

```text
Repository
[ Select repository ]

Branch

[ KEY ] [ VALUE ]
[ Add variable ]

```

### Environment-variable policy

- The user may provide zero or more key/value pairs.
- Values are encrypted or otherwise protected by the existing backend mechanism.
- Missing application-owned variables do not automatically disable Deploy.
- DeployGuard may show a warning for likely missing variables.
- The user may continue and accept that the application can fail.
- Platform-owned variables are never requested.

Example warning:

```text
This repository may require DATABASE_URL.
You can continue without it, but the application may fail.

[ Deploy Anyway ]
```

### Structural blockers

Deployment must stop before workflow dispatch and AWS mutation when:

- repository is empty
- repository or branch cannot be accessed
- language/framework is unsupported
- dependency manifest is missing
- application root is unsafe or ambiguous
- no usable build/start strategy exists
- workflow cannot be created or verified

Show one simple inline message. Do not redirect to separate Detection or Pre-flight pages.

## 7. Destroy workflow

```mermaid
flowchart TD
    A["Live application<br/>100%"] --> B["Click Destroy"]
    B --> C["Confirmation popup"]
    C --> D{"Confirm destroy?"}

    D -- "No" --> A
    D -- "Yes" --> E["Destroy running banner/popup"]

    E --> F["Dispatch GitHub Actions destroy"]
    F --> G["Terraform destroy"]
    G --> H["Remove ECS, ALB, ECR and managed resources"]
    H --> I["Reconcile S3 state and operation history"]

    I -- "Failure" --> J["Destroy failed banner<br/>View logs / Retry"]
    I -- "Success" --> K["Close running popup automatically"]
    K --> L["Show brief success toast"]
    L --> M["Project returns to Ready to Deploy"]
    M --> N["Deploy Again"]
```

### Required behavior

During destroy:

- show a persistent running popup/banner
- disable Deploy, Redeploy and duplicate Destroy
- provide a View Progress action
- preserve the live URL until destruction is confirmed complete, or clearly mark it as being removed

After successful destroy:

- close the running popup automatically
- show a short “Infrastructure destroyed” toast
- remove the live URL
- remove the 100% Live state
- keep repository analysis and configuration
- return the page to **Ready to Deploy**
- show **Deploy Again**
- preserve all deployment and destroy history

Do not fake backward progress from 100% through the deployment phases.

## 8. Canonical state model

The frontend and backend must use one shared state contract.

| State | Headline | Primary action |
|---|---|---|
| unauthenticated | Continue with GitHub | Continue with GitHub |
| GitHub App missing | Connect repositories | Install GitHub App |
| repository incomplete | Choose repository | Select repository |
| structurally blocked | Repository needs attention | Fix or choose another repository |
| ready | Ready to Deploy | Deploy |
| queued/running | Deploying | View progress |
| failed | Deployment failed | View logs / Retry |
| live | Application Live | Open Application |
| destroying | Destroying application | View progress |
| destroyed | Ready to Deploy | Deploy Again |

### Five visible lifecycle phases

```text
Analyze → Prepare → Build → Deploy → Verify
```

No legacy 23-stage denominator may influence the visible progress.

## 9. Stack detection maturity contract

Stack detection remains automatic and mostly invisible to the normal user, but it must produce a trustworthy deployment contract before any workflow dispatch or AWS mutation.

### Required detection outputs

For every analyzed repository and selected branch, persist:

- repository commit SHA used for analysis
- detected application roots
- primary application root selected for deployment
- language and runtime
- framework
- package manager and lockfile
- install command
- build command
- production start command
- application port
- health-check path
- output/artifact directory where applicable
- static, server-rendered, API, worker or mixed workload classification
- Dockerfile strategy: repository-provided, generated template or unsupported
- required and optional application environment-variable names
- persistent-storage requirement when evidence exists
- confidence level and evidence for each important inference
- structural blockers, warnings and unresolved ambiguity

### Maturity rules

- Detection must be based on repository evidence, not filename guesses alone.
- Selected branch and exact commit must be part of the detection cache key.
- A stale detection result must never be reused after the commit changes.
- Monorepositories must be scanned for multiple candidate application roots.
- The detector must rank candidates and explain why one was selected.
- Ambiguous candidates must block automatic deployment unless a safe deterministic choice exists.
- Existing user Dockerfiles may be used only after safety and deployability validation.
- Generated Dockerfiles must use centralized templates with pinned versions.
- `PORT`, `HOST`, `NODE_ENV`, AWS credentials and GitHub tokens must not be treated as user-owned required environment variables.
- Likely missing application environment variables may produce warnings without blocking Deploy.
- Missing build/start evidence, inaccessible roots and structurally unsupported repositories must block before GitHub Actions dispatch.
- Detection failures must return one concise user-facing blocker plus expandable technical evidence.
- Detection must be idempotent and reproducible for the same repository, branch and commit.
- Manual overrides must be limited, explicit, validated and auditable; they must not silently replace detector evidence.

### Supported maturity targets

At minimum, test representative fixtures for:

- Node.js with npm, yarn and pnpm
- Express or similar Node API
- React/Vite static frontend
- Next.js server-rendered application
- Python with `requirements.txt`
- Python with `pyproject.toml`
- Django
- FastAPI
- repository-provided Dockerfile
- monorepository with frontend and backend applications
- nested application root
- empty repository
- unsupported repository
- ambiguous multiple application roots
- missing production start command
- environment-variable references without provided values

### User experience

The normal New Deployment page must remain simple:

```text
Repository
Branch
Optional environment variables
Deploy
```

Detection runs silently after repository and branch selection. Only these outcomes are shown:

- ready to deploy
- non-blocking warning
- one actionable structural blocker

Full evidence is available only through Developer details or authorized diagnostics.


## 10. Legacy retirement rules

The GitHub Actions path is authoritative.

Remove or disconnect all production dependencies on:

- legacy release lanes
- Redis/BullMQ deployment queues
- deployment outbox drain
- infrastructure-plan workers
- infrastructure-apply workers
- release workers
- worker capability registration
- deployment leases and worker fencing
- legacy progress denominators
- old mutation routes
- old normal-v1 scripts
- old frontend controls

Deletion must be dependency-aware:

1. Replace every active reader/projector/route with the GitHub Actions operation model.
2. Verify builds and live routes.
3. Remove unreachable providers, scripts and source.
4. Preserve only historical database evidence required for audit/history.
5. Prove no normal product path can invoke the retired system.

## Iteration 4 — Mature stack detection and deployment-contract engine

### Goal

Upgrade stack detection from basic framework recognition into a reproducible, evidence-backed deployment-contract engine that is safe for monorepositories, nested applications and real production deployment.

### Complete journey

```text
select repository and branch
→ resolve exact commit
→ discover candidate application roots
→ identify runtime/framework/package manager
→ infer install/build/start/port/health
→ inspect Docker strategy and environment references
→ rank evidence and confidence
→ produce ready, warning or structural blocker
→ persist versioned deployment contract
```

### Required work

- audit the current detector, templates, pre-flight rules and existing fixtures
- create or harden one versioned deployment-contract schema
- key detection by installation, repository, branch and exact commit SHA
- invalidate stale results when branch head or relevant configuration changes
- support multiple candidate roots and monorepository ranking
- preserve evidence for every important inference
- distinguish hard evidence, inferred defaults and unresolved ambiguity
- detect language, framework, package manager, lockfile and runtime version evidence
- infer install, build and production start commands
- infer application port and health path without asking users for platform-owned values
- detect static, SSR, API, worker and mixed workload shapes where supported
- inspect repository Dockerfiles and select safe repository-provided or generated strategy
- extract likely application-owned environment-variable names without exposing values
- exclude `PORT`, `HOST`, `NODE_ENV`, AWS credentials, GitHub tokens and platform-owned settings from user-required ENV
- produce non-blocking ENV warnings and blocking structural failures
- prevent workflow dispatch and AWS mutation when the deployment contract is structurally unsafe
- persist detector version, evidence, confidence, warnings, blockers and selected root
- expose concise user outcomes and expandable Developer details
- create representative repository fixtures covering the maturity targets in Section 9
- remove contradictory duplicate detection logic from frontend or legacy services

### Done when

- the same repository, branch and commit produces the same deployment contract
- a changed commit is re-analyzed rather than receiving stale results
- Node, React/Vite, Next.js, Python, Django and FastAPI fixtures pass
- npm, yarn, pnpm, `requirements.txt` and `pyproject.toml` cases pass
- nested roots and monorepositories are ranked correctly
- ambiguous multi-root repositories stop with one actionable blocker
- a repository Dockerfile is validated before selection
- generated Docker strategy uses centralized pinned templates
- likely missing application ENV produces a warning but does not disable Deploy
- structurally impossible repositories stop before workflow dispatch and AWS mutation
- full evidence is available in authorized diagnostics while the normal UI remains simple
- backend/frontend builds and detector regression suites pass
