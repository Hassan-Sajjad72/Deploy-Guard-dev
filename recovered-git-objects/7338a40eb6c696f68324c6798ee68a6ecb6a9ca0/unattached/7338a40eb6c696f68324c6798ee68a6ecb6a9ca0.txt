## Iteration 4 completed result

- A deterministic, fail-closed operator read model now classifies existing
  project evidence as `valid`, `adoptable`, `recoverable`, `safe_residue`, or
  `ambiguous`. A genuinely clean project remains unclassified, so its normal
  Deploy eligibility is unchanged.
- `valid` requires one canonical stable release plus fresh verified live/healthy
  cloud evidence, provisioned infrastructure, consistent Terraform state, and no
  active lease, cross-lane owner, claim, queue item, or legacy run. `adoptable`
  requires the same healthy identity without a canonical stable projection.
- `recoverable` is limited to the same immutable active normal-v1 intent and
  never creates a replacement identity. `safe_residue` requires a completed
  destroy, fresh inventory, only verified residue/shared-platform categories,
  no unknown resources, and a clear execution scope. Every other existing state
  fails closed as `ambiguous`.
- The classification is available only from the admin-guarded detailed/current-
  state boundary and the new admin-only
  `GET /api/projects/:projectId/current-state/existing-state` projection.
  Ordinary developer current-state responses contain none of its codes, cleanup
  actions, inventory, ownership, or state evidence.
- A valid stable deployment can still project Live/Redeploy. Adoptable, residue,
  and ambiguous evidence projects only neutral platform attention. The previous
  projector defect that could expose a stable URL without verified cloud state
  is corrected: unverified existing state retains historical release identity
  but no live URL.
